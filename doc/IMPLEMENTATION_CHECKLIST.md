# 実装チェックリスト・生成 AI への引き継ぎ

別チャットの生成 AI に **このフォルダ一式** を渡し、「[README.md](./README.md) の順に読んで実装して」と指示できることを想定する。

## 1. 必読ドキュメント（順序固定推奨）

1. [README.md](./README.md)
2. [REQUIREMENTS.md](./REQUIREMENTS.md)
3. [SPEC_MAPPING_AND_MIXING.md](./SPEC_MAPPING_AND_MIXING.md) — **数式・定数の正**
4. [TECH_STACK.md](./TECH_STACK.md)
5. [BUILD_AND_DEPLOY.md](./BUILD_AND_DEPLOY.md)

## 2. 実装タスク（分解）

- [ ] **定数**: MIDI 鍵盤の表示範囲（最小・最大）、`oct_ref`、固定 S/V またはオクターブ補正式
- [ ] **midi.ts**: `midi ↔ 音名+オクターブ`、`midi % 12` で音クラス
- [ ] **noteToColor.ts**: 音クラス → `H₀`、HSV→sRGB、単音 RGB
- [ ] **mixing.ts**: 加法（正規化付き線形和）、CMY 乗算型、0 音の挙動
- [ ] **UI**: 鍵盤（トグル選択）、カラーボックス、加法/減法トグル、RGB/HEX/H 表示
- [ ] **テスト**: 単音の代表値、和音の可換性、混色モード切替
- [ ] **レスポンシブ**: スマホ幅でのレイアウト
- [ ] **README（実装リポ）**: 起動方法、デプロイ先 URL

## 3. コーディング開始前に「決めておくとよい」未決事項

以下は [SPEC_MAPPING_AND_MIXING.md](./SPEC_MAPPING_AND_MIXING.md) で推奨値を与えているが、**プロダクト判断で変えてよい**。変えたら **仕様書と定数を同時更新** すること。

| 項目 | 内容 |
|------|------|
| 鍵盤の範囲 | 例: MIDI 48–83。88鍵全部にするか、1オクターブだけのデモにするか |
| オクターブと明度 | 固定 HSV のみにするか、`V` のオクターブ補正を入れるか |
| 加法の正規化 | 「max で割って 255 にスケール」か「平均」か — 仕様書の推奨に従うか明示 |
| 選択 UX | 鍵のトグル + 「全クリア」ボタンの有無 |
| 言語 | UI 文言を日本語のみにするか、英語併記するか |

## 4. 生成 AI に依頼する際のプロンプト例（コピペ用）

```
次のディレクトリに仕様書がある。README の順に読み、要件を満たす Web アプリを実装してください。
仕様の数式は SPEC_MAPPING_AND_MIXING.md を正とする。
技術スタックは TECH_STACK.md に従い、Vite + TypeScript を使う。
ドメイン層（色変換・混色）を UI から分離し、Vitest でテストを書く。
```

（実際のパスをユーザーが添付する想定。）

## 5. 仕様と実装のズレを防ぐルール

- **色の定義**は `constants.ts` 等に **H₀ テーブルを1箇所** に集約する。
- **混色**は `mixing.ts` のみから呼ぶ（コンポーネント内に直書きしない）。
- 仕様変更時は **先に SPEC を更新** し、次にコード。

## 6. セキュリティ・プライバシー

- 外部 API に音データを送らない（要件どおり）。
- 依存パッケージは `npm audit` を定期的に確認（CI に含めるとよい）。

- テーマ（ダークモード）と鍵盤のコントラスト自動調整
